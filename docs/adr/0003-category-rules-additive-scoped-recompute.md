# Additive multi-category rules with per-tag, per-rule provenance

A Transaction can carry multiple Categories (many-to-many), not one. Category Rules follow the same shape: each Rule produces exactly one Category, but every Rule whose match condition hits a Transaction applies — there is no precedence or ordering between Rules. A Transaction matched by three Rules simply ends up with three Categories. This was chosen over a traditional single-category-wins-by-priority model because multi-category was already wanted for manual tagging (e.g. a Costco run as both Groceries and Household); once Categories are additive, forcing Rules to pick a single winner would be an artificial restriction the storage model doesn't otherwise need.

Each Transaction-Category tag records its provenance: the Rule that produced it, or null for a manually-added tag. This is what makes the recompute behavior work — editing or deleting a Rule re-runs only that Rule and adds/removes only the tags it produced, never touching tags from other Rules or tags the user added by hand. The alternative (recompute everything on any Rule change, or never recompute at all) was rejected: a full recompute risks clobbering manual corrections if provenance weren't tracked at all, while no recompute means an edited Rule silently stops applying to already-imported Transactions, which defeats the point of editing a Rule. Per-tag provenance is a small amount of extra schema (a nullable rule_id on the join row) for retroactive correctness without the blast radius of a full recompute.
