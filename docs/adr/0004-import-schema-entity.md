# Import Schema as one mechanism for built-in and custom file mappings

Real eToro/Revolut/bank exports (per the CSV import formats research) disagree on file format (multi-sheet `.xlsx` vs. flat CSV), preamble/footer rows before the real table, column names and their meaning (the same header can mean different things across a single bank's own report types), date and decimal conventions, and whether a `Type`/state column reliably identifies what a row is. No per-institution hardcoding scheme could keep up with that, and generic bank statements have no canonical shape to hardcode against at all.

We introduce **Import Schema** as the one entity that describes how to translate a specific file shape into Transactions: table-location (sheet, header-row offset), per-field column-or-fixed-value bindings, explicit parsing hints (date format, decimal style — never auto-detected, since day-first/month-first dates are genuinely ambiguous and a wrong guess would silently corrupt net-worth history), a row-exclusion rule, and an external-flow classification rule. Built-in Schemas for eToro and Revolut are just pre-filled instances of the same mechanism a user gets when defining their own Schema for an unrecognized bank — there is no separate hardcoded path. A Schema is scoped to a file shape, not an Account, so one Schema is reused across every Account fed by that shape (e.g. two Revolut currency-pocket Accounts), with the target Account picked at each import.

Each import is recorded as an **Import Run** (Schema used, source file, timestamp, row count), and every Transaction it creates carries a raw-row copy, a key derived from that row, and a link to its Import Run. This makes re-importing an overlapping statement safe (the derived key prevents duplicates) and a bad import fully reversible (delete everything tied to that run), at the cost of a small amount of schema per Transaction.
